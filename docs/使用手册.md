# SiliconHQ for DeepSeek Harness

在关联本地目录的 DSH 聊天中输入 `/sihq` 并回车。选择已保存的流程后，展开「查看调用指令」即可复制命令。本手册适用于插件 `0.14.4` 和 DSH Desktop 宿主包 `0.2.2-rc.5`。

## 启动并查看运行

1. 选择工作流，核对预览中的工作目录、执行者和步骤顺序。「启动前检查」会列出需要处理的问题，例如缺少已选后端、步骤需要只读能力或项目需要 Git 工作树。检查本身不调用模型。切换工作目录、修改后端配置或预览过期后，点「重新检查」。弹窗保留任务文字，重新载入当前目录、执行者和可用引用。再次勾选需要交给 Agent 的资料。试用草稿时沿用打开弹窗时的草稿。
2. 在「任务」中填写需求，再点「开始执行」。在工作流的「更多操作 → 查看调用指令」复制 `/sihq workflow --template <模板 ID> "任务"`。模板改名后仍可使用这条指令。`/sihq workflow "任务"` 则使用当前默认流程。
3. 启动后看聊天右侧「当前工作流」。运行中的步骤会显示执行者，项目验证会显示退出码。遇到人工确认时，点「处理审批」跳到待办处，核对上游证据后批准、拒绝或退回。后台日志和取消操作在 DSH Jobs 中。
4. 展开一个 Agent 步骤。「指派」来自这次运行保存的配置。「DSH 解析」来自宿主的子 Agent 选项或子会话描述，「实际请求」来自该子会话首次委派的请求记录。外部产品如有回报，会显示「执行者回报的模型」。只有指派信息时，实际模型显示「未报告」。重试或改派后展开「历史尝试」可核对原来的实例、模型证据和错误。
5. 刷新保留已经打开的流程和所选轮次。选择历史轮次可以查看当时的报告，回到「最新」可处理当前审批。如果已经关掉标签，在原聊天输入 `/sihq`，选「本会话运行记录 → 查看详情」。也可从 DSH 右侧栏的新标签页打开「当前工作流」，进入本会话最近更新的运行。未启用右侧栏的 profile 通过聊天输入框上方的回执查看详情。

### 引用项目约定

启动或继续下一轮时，展开「引用上下文 → 项目文档」。进入目录点击「引用」或输入相对路径，支持 UTF-8 的 `.md` 和 `.markdown`。点「查看文档原文」核对版本，可以取消勾选。点击引用时冻结内容，此后即使工作区发生修改，本轮各个实例仍收到预览中的版本。需要最新内容时再次引用文件。要检查实际交接，在运行详情打开步骤的「查看实际委派输入」。新一轮可以重新选择。

如果当前工作目录有 `RULES.md`，且 DSH 宿主可执行 Hypo-Workflow 的 `hw`，输入功能关键词并点「用 hw 查找相关需求」，再点选匹配项。普通项目可以直接选择 Markdown。要把文档一致性检查作为通过条件，可在已接入 Hypo 的工作流中添加「运行验证命令」，程序填 `hw`，参数依次填 `check` 和 `--json`。查看报告中的 alarms 和 hints；未接入项目也可能以退出码 0 返回提示。

### 把讨论和上轮报告带入任务

例如，聊天里已商定空配置应返回哪些默认值。启动时，可以填写「按所选约定实现空配置」，展开「引用上下文」，勾选说明默认值的那段用户或助手消息。在运行详情选择「继续下一轮」时，也可以引用该流程上一轮的验收报告。需要审查当前改动时，点击「载入并引用当前 Git diff」。确认提交前可展开来源原文核对。选择的内容会随本轮运行保存，并交给执行该任务的 Agent。

内置开发流程续轮时默认使用新任务和本次所选引用。要让计划、开发和审查各自收到自己的上一轮报告，勾选「各角色继承各自的上一轮报告」，或在聊天输入 `/sihq workflow continue <流程ID> --inherit-reports "新任务"`。本轮返工会收到本轮最近一次成功的开发报告和新的审查意见。要让所有步骤看到同一份报告，在「引用上下文」中勾选该报告。展开或勾选时才读取原文。

`fork` 还会继承父会话已完成的历史。其他执行者可以从显式引用取得完成本步所需的背景。在运行详情展开步骤，再打开「查看实际委派输入」，可以核对本次派发的提示词、输出约束和引用内容。旧记录可继续查看已保存报告，当时未保存的输入无法补录。

在弹窗中选择的 diff 随本轮任务冻结。审查员需要看到开发步骤刚写入的文件时，在审查步骤启用「执行本步骤时读取最新 Git diff」。直接使用 `/sihq run "流程名" "任务"` 会采用模板设置；需要勾选聊天片段时，请使用交互式启动窗口。

## 角色设置

打开 **插件 → 已安装插件 → dsh-sihq → SiliconHQ 工作流**。打开「SiliconHQ 开发流程」的「编辑」，为计划、开发与修复、审查等角色选择子 Agent provider，设置最多修复次数并保存。默认都使用 `spawn`，最多修复两次。保存写入当前 DSH profile 的配置补丁。每个流程在启动时保存角色路由，恢复和继续下一轮沿用该路由。DSH 或外部 provider 自身的默认模型仍可由其管理员更新。

| 选择 | 用途 | 模型和权限 |
| --- | --- | --- |
| `spawn` | 全部角色 | 沿用父会话的模型路由，也可在角色或自定义步骤选择 DSH 模型供应商、模型及该模型支持的思考强度。只读阶段使用插件随包提供的 `sihq-readonly` Agent 预设，仅带文件读取和搜索工具。 |
| `claude-code`、`codex` 或其他已注册的外部 provider | 开发与修复 | 启用对应的 DSH 子 Agent 插件。直接选基础后端时使用该 provider 的配置。要为同一官方 Claude Code 或 Codex 后端配置多个模型，可先创建命名实例，再将角色指向该实例。 |
| `fork` | 开发与修复 | 带入父会话截至上一轮结束的历史，继承父预设。在该插件中仍可通过 DSH 的 agentOptions 选择模型和思考强度。 |
| `sihq-codex-readonly` | Codex 计划或审查 | 通过 DSH subprocess 调用已安装的 Codex CLI，显式传入 `--sandbox read-only`。使用 Codex 自己的登录，可按步骤覆盖模型和思考强度。选项来自已安装 CLI 的内置目录，自定义模型可填写 ID，Windows 的 PATH 需要可执行的 Codex。 |

模型和强度留空时采用后端默认值。若已用 DSH 的 `providerName` 分别注册多个 provider，也可直接按注册名在步骤里选取。

例如，计划选 `spawn`，开发选 `claude-code`，审查选 `sihq-codex-readonly`。输入 `/sihq providers` 可检查当前角色和常用 provider 的注册状态。外部后端每次收到新的委派，各阶段以原始需求、已校验的报告、审查意见和工作树状态交接。默认流程用尽修复预算后，由设置中指定的只读反馈角色生成开发反馈，再由计划角色汇总。只读审查员根据已有证据评审。在内置流程中可让开发角色运行测试，在自定义流程中还可以添加「运行验证命令」。

## Agent 实例

打开 **SiliconHQ 工作流 → 管理 Agent 实例**。「已注册的基础后端」列出当前 DSH 可调用的执行者和直接使用它们的工作流步骤。「我的命名实例」列出你保存的配置。点击某个后端的「基于此后端新建实例」，填写名称并选择模型和思考强度。可以为同一后端建立多组配置，例如「快速开发」和「深入开发」。第三方后端通过 DSH 公布的能力决定可配置项。

回到工作流，在步骤或内置角色的「执行者」下拉框选择以「实例」开头的项。实例列表显示其基础后端、模型、强度和使用位置。修改或改名后，引用它的工作流在下次启动时使用新值。删除仍被引用的实例时，可以一次性替换所有引用，也可以先返回工作流逐项修改。历史运行和恢复从已保存的路由快照读取显式设置。

如果已保存的实例出现「需要修复」，从该行点「修复实例」。遇到重复 ID 时可按卡片的原始行号区分，并为选中的实例生成新 ID。仍有流程引用的唯一实例，先保留其 ID，或先修改这些流程的执行者。若后端注册名已经换绑其他产品，打开实例核对新后端；选择「使用当前注册的后端」后重新选择模型、强度和预设并保存。

同一模型也能承担不同职责。对于支持独立预设的后端（例如 `spawn`），在命名实例的「DSH Agent 预设」选择当前宿主已经注册的预设，让开发步骤获得该预设的工具和指令。要把实例用于只读步骤，应留空让插件选用 `sihq-readonly`，或明确选择它。继承父会话预设的 `fork` 和官方 Codex、Claude Code 产品后端按各自的能力提供工具。

启动预检和实际派发会核对当前的后端注册、有效预设与权限。例如，官方 Claude Code 的 `permissionMode: plan` 无法承担开发步骤。支持宿主深度上限的后端还会遵守 DSH Subagent 配置中的 `maxDepth`；深度已经用完时，减少嵌套或调整宿主设置后再提交。外部产品的委派深度由其后端管理。

DSH 的 spawn、fork 走原生模型路由。第三方后端声明 `agentRouteDefaults` 时，供应商和模型采用后端默认值；实例可以覆盖模型或仅选择思考强度。只读 Codex 使用本机 CLI 的模型目录。官方 Codex 开发后端使用该 provider 自带 CLI 的模型目录和 `model_reasoning_effort`。Claude Code 支持常用模型别名和完整模型 ID，强度通过 `CLAUDE_CODE_EFFORT_LEVEL` 传给该次子进程；实际可用模型和强度由账户和客户端决定。产品实例沿用基础 provider 的环境和工具权限。留空的选项沿用后端默认值。[Claude Code 模型设置](https://code.claude.com/docs/en/model-config) · [Codex 配置参考](https://developers.openai.com/codex/config-reference/)

**验证一个已保存的实例。** 在「我的命名实例」找到该实例，选择「更多操作 → 检查配置」。面板分别显示「后端注册」「模型路由」「实际委派」。前两项使用当前 profile 的 provider 和模型目录进行检查，目录无法核对的设置会标明原因。此时「实际委派」显示尚未执行。

要确认本机账号和模型能完成一次调用，点击「实际委派测试」。插件会在独立测试会话和临时空目录中调用该实例，要求回复 `SIHQ_OK`。这个按钮会产生实际调用，可能消耗额度。外部执行者沿用该 provider 的工具权限。测试完成后，插件清理临时目录，DSH 按 profile 的会话持久化设置保存诊断记录。通过表示实例完成了这次简短请求。工作流中的修改文件和运行测试仍取决于后端权限。

## 自定义工作流

设置首页列出当前 profile 的工作流，默认流程旁有「默认」标记。如果导入或手工编辑的模板含失效引用，在相应卡片点击「修复工作流」，按诊断更正后点「保存修复」，也可删除该模板。其他有效模板仍可从聊天启动，运行记录仍可打开。

- **新建或复制**。点击「新建工作流」，选择空白或开发与审查预设。也可以在某条自定义流程的「更多操作」中复制它。副本有独立 ID，保存后才出现在聊天的流程列表。
- **编辑步骤**。点击「编辑」，展开步骤即可修改名称、执行说明、执行者、模型、报告来源和审查退回目标。可以在指定位置插入步骤。若移动会让输入或退回目标落到后面，先改掉相应引用。删除被引用的步骤时，面板列出会失去输入或退回目标的步骤，确认后才修改草稿。
- **编写执行说明**。开发、计划、审查和只读分析步骤都有「插入说明示例」。选择示例会把完整文字追加到现有说明末尾。可直接编辑或删除，展开「查看 Agent 输入与输出要求」即可预览。示例不会改变步骤类型、执行者或输入报告的勾选。
- **检查与试用**。「查看 Agent 输入与输出要求」展示插件提交给执行者的提示词和报告格式。可切换到适用的自动退回、人工退回或再次复审场景，并勾选启动时的参考资料。聊天任务、上游报告和 Git 改动用占位内容表示。执行者自己的系统指令由 DSH 或外部 Agent 管理。点击「在聊天中试用草稿」，然后在同一客户端的项目聊天输入 `/sihq`，选择标为「草稿」的流程。试用会真实执行步骤。
- **保存和运行**。保存后返回列表。在项目聊天输入 `/sihq` 并回车，选流程、填任务并开始执行。在「更多操作 → 查看调用指令」可复制带稳定模板 ID 的命令。也可以在聊天中输入 `/sihq run "流程名" "任务"`，按当前名称运行。
- **设为默认或删除**。「更多操作 → 设为默认」立即生效。删除当前默认流程时，先选择新的默认流程，再确认删除。已有运行和历史记录保留各自的流程快照。内置「SiliconHQ 开发流程」始终可用，可以编辑角色，也可以从开发预设新建。

在两个页面同时编辑时，不同项的变更可以一起保存。如果相同设置在另一个页面也被修改，草稿会保留。展开「同一项已在其他页面修改」中的冲突项，对照「我的草稿」和「当前已保存」，选择要采用的值，再保存。这个选择只作用于重叠的修改。

初始配置中的 `diff-review` 只启动一次只读审查，覆盖已暂存和未暂存的受跟踪改动。新建且尚未加入 Git 的文件不在这份 diff 里。审查通过后可在流程记录中查看逐条证据。

在工作流编辑器勾选「每轮启动时冻结 Git diff，交给本轮 Agent」，这一轮的每个 Agent 都会收到同一份基线。采集范围是本次聊天选定的工作目录及其子目录。菜单在启动预览时采集，直接输入指令时在提交前采集；续轮会生成新基线。若要让审查员看到开发步骤刚产生的修改，在该审查步骤勾选「执行本步骤时读取最新 Git diff」。步骤级 diff 到执行该步骤时才读取；两项可以同时启用，历史中的实际输入会区分两份资料。恢复步骤沿用它已取得的输入；显式重试时重新读取步骤级 diff。

### 选择审查策略

在自定义工作流展开「独立审查」步骤，或编辑内置「SiliconHQ 开发流程」，找到「审查策略」。默认的「严格验收」要求所有已报告缺陷处理完毕。「按阻塞级别验收」按报告证据决定结果。

| 报告内容 | 运行结果 |
| --- | --- |
| P0 隐蔽的严重错误、P1 可见的功能故障，或已失败的测试与验收标准 | 需要修改。按照已配置的分支、退回步骤和修复预算处理。 |
| 必要验证缺失或审查员明确标记受阻 | 无已证实缺陷时显示受阻，可补充证据后复核。 |
| 验收通过，仅有 P2 维护建议或 P3 改进偏好 | 通过，保留建议，不触发修复。 |

在「当前工作流」展开审查步骤，可查看阻塞项和后续建议的级别、位置、依据和修改建议。复核会收到上次的阻塞项与待验证事项。审查策略随本次流程冻结，也随工作流导出。

### 在开发前由人确认

在计划和开发之间插入步骤，将「步骤类型」选为「人工确认」。在「确认提示」填写要核对的问题，并在「输入报告」勾选计划。该步骤由人处理，无需选择 Agent。

在等待确认的详情中展开「查看完整任务和本轮引用」，核对任务原文和本轮选入的资料。再展开「核对上游报告」查看指定步骤的完整结果。上游步骤本轮已跳过时，审批区会显示该步骤的名称和跳过状态。

运行到此步骤时，流程保存进度并释放工作区锁。在原聊天的运行详情阅读上游报告，可在「决定说明（可选）」留下理由。点击「继续运行（批准）」会继续后续步骤。点击「拒绝继续」会终止本轮并记录决定。退出客户端后仍可回到这条记录处理。每次等待都有独立的确认 ID，已处理的确认不能重复使用。

若计划或实现还需修改，请填写具体理由，在「退回目标步骤」选择要重做的步骤，再点击「退回修改」。可选择上一次实际通过的人工审批之后、当前审批之前已经完成的串行 Agent 步骤。流程从目标步骤重新执行，到达当前审批时会要求你重新核对。如果路径包含开发步骤，Agent 会再次在当前工作树上工作。退回消耗本轮修复额度，原决定、旧报告和修改后的报告都留在记录中。

### 失败后更换 Agent 实例

例如，开发步骤因模型额度不足而失败。先检查工作树和失败步骤的实际输入。在同一运行的详情中点击「改派失败步骤」，选择待处理步骤和新的命名实例，勾选「已核对工作区，允许重新委派」，点击「确认改派」。实例列表会检查该步骤所需的读写能力，无合适实例时可在插件设置中添加，再回到详情刷新列表。

展开「查看不可选实例及原因」可以看到每个实例为何被排除。同一实例改名后仍可用「重试」执行。改派只作用于选中的尝试。该步骤执行期间可能已经写入的文件会保留，已完成的步骤和并行成员也会保留。在步骤详情中展开「历史尝试」，可核对原执行者、当时保存的输入和失败原因。内置流程可改派当前失败或取消的阶段，自定义流程可在当前批次中逐个选择。以后新启动的运行继续使用模板配置。

### 将工作流带到另一个 profile

1. 在源 profile 的工作流列表打开该流程的「更多操作 → 导出工作流」，保存下载的 `*.sihq.json`。文件包含流程定义、它引用的命名实例以及当时的修复总上限。分享时也会分享写进步骤的执行说明。账号、API key、运行记录和其他未引用的实例不随包传递。
2. 在目标 profile 打开「SiliconHQ 工作流 → 导入工作流」，选择刚才的文件。在「目标实例」可选择兼容的已有实例、「自动匹配，缺少时新建」或「新建独立实例」。例如，目标机器已有「本机评审」，可以直接让导入步骤引用它。需要保留源设置时，按提示映射「目标后端」。目标机器的凭证由其 provider 管理。
3. 点「检查导入」，核对准备新建和复用的实例。若目标环境没有对应的模型或预设，可选择兼容的目标实例，或选择目标后端的默认供应商、模型、强度和预设，再次检查。点「确认导入」保存。每次导入自定义流程会生成新的流程 ID，自动匹配允许多条流程共用同一个实例。回到项目聊天，输入 `/sihq` 选择刚导入的流程。
4. 导入内置「SiliconHQ 开发流程」时，预览会逐项列出角色的旧值和新值。确认要更新该 profile 的角色后，点「应用到内置流程」。若两个 profile 的修复总上限不同，只有主动勾选同步才会更新它，这一选择影响目标 profile 的所有工作流。

### 并行只读步骤，按报告结果选分支

在编辑器里把两项相互独立的「只读分析」「计划」或「独立审查」排在一起，展开后一项，点击「与上一步并行」。同组至少有两个相邻步骤，允许共享更早步骤的报告。组员之间不能把彼此选作输入或条件来源，组内审查也不能设置退回目标。「移出并行组」可恢复顺序执行。后续步骤在整组结束后运行，开发步骤始终串行执行。

当 DSH 的子 Agent 名额已满时，尚未接纳的步骤显示「等待执行名额」。已有任务释放名额后会继续派发，也可以从 Jobs 取消等待。等待超时后可在名额空出时恢复。对已经派发、结果不确定的步骤，要先检查工作区，再决定是否显式重试。

例如，让「代码审查」与「文档检查」并行，组后安排一个「开发」步骤。在开发步骤的「执行条件」选择「代码审查」，在「满足以下结果时执行」选择「需要修改」。另建一个只读步骤选择同一来源和「审查通过」。开发与只读步骤会分别按各自条件执行，运行详情会标出跳过的步骤。

- 条件可读前面开发报告的「已完成开发」「未完成开发」、无退回目标的审查报告的「审查通过」「需要修改」「证据不足」，以及无退回目标的验证命令的「验证通过」「验证失败」。每个步骤可选一个来源和一个结果。「始终执行」会取消这个条件。
- 开发报告为「未完成开发」时，流程会保存已做的改动、验证和遗留事项。想专门处理这种情况，可增加一个步骤，以这个开发步骤为条件来源，选择「未完成开发」作为触发结果。该分支实际完成后才算处理了这一结果。如果没有分支接手，流程最终会保留「开发未完成」，即使后面的常规汇总已经完成。可以带着遗留事项继续下一轮。
- 审查结论是「需要修改」或「证据不足」时，须有后续条件明确处理这个结果，流程才会继续到分支。没有匹配分支时，仍按该审查配置退回、停止或等待恢复。
- 审查退回的目标仍遵守该步骤的执行条件。如果本轮条件未命中，流程会保存原审查结论和无法退回的原因。DSH 接纳实际修复委派后才消耗一次修复额度。内置和自定义审查都要求「需要修改」有相应的缺陷证据。
- 条件来源本身被跳过时，依赖该条件的步骤也会跳过。后续汇总步骤可以勾选多个分支作为「输入报告」，执行时只交付实际产生的报告。组内某项失败时，已成功成员的报告会保存供恢复使用。

### 让测试结果决定流程能否继续

在「开发」后面新增「运行验证命令」步骤。例如，项目用 Node.js 自带的测试框架时，将「可执行文件」填为 `node`，再点「添加参数」填写 `--test`。只测某个文件时，再加一个参数填写项目内的测试文件路径。含空格的路径也填进一个参数框。超时默认 120 秒，可设为 1 至 3600 秒。

这一步由当前 DSH 会话的 shell 工具在启动时确认的目录执行，沿用宿主的权限和沙箱设置。默认以退出码 0 作为通过条件。要让测试驱动返工，在这条验证步骤的「验证失败时退回」选择前面的开发步骤，将「该步骤最多退回次数」设为 1，并确保流程还有修复额度。测试以非零退出码结束时，开发 Agent 会收到失败输出，之后按原顺序再次运行测试。也可以在后续步骤选择「验证失败」分支，例如只分析失败原因。验证程序未能启动、超时、取消、权限拒绝或执行结果未知时，流程会停止并保留修复额度。若宿主把验证转入后台，右侧详情会显示正在停止的任务 ID，确认停止后再释放工作区。详情中可以查看实际程序和参数、退出码、用时、标准输出和标准错误，过长的输出会标明截断。失败或中断后，核对工作目录再显式重试，先前尝试会保留。恢复期间取消等待，后台仍会等旧验证任务退出后释放工作区。

设置的超时还受 DSH 前台工具时限约束。宿主若将命令转到后台，流程会停止该任务，并记录未能取得前台退出结果。Windows 的 `.cmd` 和 `.bat` 启动器仅支持简单参数；需要原样传递引号等特殊字符时，请选择实际的 `.exe` 程序。启动预览与工作流导入预览都会列出将要运行的命令。

需要交给审查员时，在后面的「独立审查」步骤将这条验证选作「输入报告」。审查员会收到命令执行证据。验证步骤本身按保存的程序和参数运行，聊天文字与模型回复不会变成命令参数。

## 命令

```text
/sihq
/sihq run "只审查当前 diff" "检查错误处理和测试覆盖"
/sihq workflow "修复配置加载并运行测试"
/sihq workflow "分析并实现新的校验" --max-repairs 1
/sihq workflow templates
/sihq workflow --template diff-review "核对 README.md 的端口改动"
/sihq workflow list
/sihq workflow status <流程 ID>
/sihq workflow resume <流程 ID>
/sihq workflow retry <流程 ID>
/sihq workflow reassign <流程 ID> <失败尝试 ID> <命名实例 ID> --confirm
/sihq workflow approve <流程 ID> <确认 ID> "已核对计划"
/sihq workflow return <流程 ID> <确认 ID> <目标步骤 ID> "请补充空配置的测试计划"
/sihq workflow reject <流程 ID> <确认 ID> "需求已取消，结束本轮"
/sihq workflow continue <流程 ID> "增加空配置测试"
```

在创建流程的项目和会话中使用这些命令。`list` 显示本会话的运行，如有下一页，会给出带 `--offset` 的命令。`status` 可读取当前记录，等待人工确认时，确认 ID 在 `pendingApproval.id`。详情按钮会自动使用对应 ID。批准和终止时可以省略理由，退回修改时须填写理由。

`resume` 尽量复用已保存的结果。上次中断后若无法确定子 Agent 是否已改动文件，或报告校验失败，请先检查工作树和阶段日志，再用 `retry` 明确重新派发该阶段。详情的重试按钮列出本次将重试的步骤。其他窗口已经处理同一次失败时，旧按钮会提示刷新。直接输入只带流程 ID 的重试命令会选取提交时的失败步骤。普通恢复会保留待办的人工确认。完成一轮后可用 `continue` 提交追加需求并保留旧轮次的报告。

## 兼容入口

DSH 的 Jobs 默认会在后台任务结束时唤醒聊天主 Agent。Jobs 和流程记录保存的是各阶段结果，主 Agent 随后发言或修改文件属于独立的一轮。需要让空闲的主 Agent 等你发言时，可在 DSH 的 `tool-jobs` 配置使用 `completionDelivery: quiet`。该设置影响同一配置范围内其他后台任务。Claude 开发阶段依赖官方 Claude Code provider 的工具权限；使用默认的 `dontAsk` 时，未预先授权的写入可能被拒绝。无人值守的编辑可按需在该 provider 配置 `permissionMode: acceptEdits`。

单任务 `/sihq run "任务"`、`plan|implement|review|resume`、旧流程及 GPU kernel 命令继续使用随包编译的 SiliconHQ CLI，采用原项目的 `sihq.config.json` 和 Codex 配置。记录与原版共用用户目录下的 `.llm-coder`。终端交互模式和持续日志可用 `node dist/cli.js chat`、`node dist/cli.js kernel logs <id> --follow`。GPU 实验依赖原项目指定的 Linux、CUDA 环境。

聊天里的 `/sihq list` 列出当前项目的单任务记录，`/sihq workflow list` 列出当前项目、当前会话的流程。按 ID 继续单任务时，请打开所属项目。Git worktree 的根目录和子目录共用开发锁；两个独立 worktree 可以分别运行任务。

非 Git 项目的父目录和子目录也会互斥，两个兄弟目录各自可以运行。若旧版锁只记录了进程号，进程存活时会保留锁。人工决定以已经提交的检查点为准。Windows 上如果 `workflow.json` 暂时被其他程序占用，JSON 导出会稍后补写。可回到运行详情核对已保存的决定和状态。

## 安装和开发

从 Desktop 的插件页添加本地 npm 包，或在退出 Desktop 后用随安装提供的 CLI：

```powershell
& "$env:LOCALAPPDATA\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd" plugin --profile desktop add "file:D:/dsh-sihq-workspace/dsh-sihq"
```

从源码安装时，先准备 Node.js 22.13 或更高版本，在项目根目录执行 `npm ci` 和 `npm run build`，再添加本地包。`npm test` 运行项目回归测试。[SiliconHQ 上游使用手册](../UPSTREAM.md)

要在真实 DSH 界面使用本地测试模型验收，先安装兼容的 DSH 和 Chromium 浏览器，在项目根目录执行：

```powershell
npm --prefix tests/host ci
node tests/host/run.mjs
```

在 Windows 上，脚本会查找已安装的 DSH Desktop 和 Edge，并将临时 profile、测试项目和日志放在插件目录外。默认先生成 npm 安装包，验收结果目录的 `release.json` 记录宿主版本、包路径、SHA-256 和权限模式。用 `--source` 可测试开发目录，`--package <tgz路径>` 可验收特定安装包，`--out <目录>` 可指定已存在的外层目录，`--browser <可执行文件>` 可指定本机的 Chromium 浏览器。

验收脚本的 `--permission-mode` 只作用于临时 DSH profile，默认 `workspace-write`。Windows 沙箱若拒绝给测试目录设置 ACL，验证步骤会记录宿主错误并停止流程。本版的只读测试程序可用 `--permission-mode read-only` 验收，包括真实命令返回 0 和 7 的两条路径。会生成缓存、产物或快照的项目测试需要宿主允许写入相应目录。

宿主返回 `SANDBOX_PREPARATION_FAILED` 时，步骤详情会显示「宿主沙箱准备失败，验证命令未启动」，并保留诊断。修复宿主环境后可重试。只有真实的程序非零退出会触发为命令失败配置的返工。

`--shell-probe` 单独核对 DSH shell 的实际输出、退出码和后台任务停止证据。要复现特定宿主错误，可加 `--expect-shell-error SANDBOX_PREPARATION_FAILED`。社区后端的目录兼容性验收使用 `--product-package <Product Subagents 0.4.1 的 tgz 路径>`，测试使用本地模拟产品。
